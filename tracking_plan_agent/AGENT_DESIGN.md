# 埋点方案生成 Agent · 设计方案 v0.1

> 目标：用户输入新埋点需求 → agent 参照历史方案的规范与口径 → 生成可直接交付研发的新埋点事件设计行（与历史 xlsx 同构）
> 依据：2026-09-20 GitHub 调研结论 + 2026-09-21 history_file.xlsx 真实样本解析

## 一、数据基础：三份东西

```
tracking_plan_agent/
├── corpus/                 # 历史方案语料（结构化）
│   ├── sample-001.md       # 已录入：模式选择入口
│   └── sample-002+.md      # 待补：后续每行历史方案一行一文件
├── conventions.md          # 命名与口径规范（从语料提炼，持续沉淀）
└── agent/
    ├── SKILL.md            # agent 工作流定义
    └── templates/
        └── output_row.md   # 输出行模板
```

## 二、输出契约（对齐历史表 6 列）

生成结果必须能直接粘回 WPS 表格，列结构：

| 列 | 生成规则 | 依据规范 |
|---|---|---|
| 指标名 | `【迭代/功能名】+ 模块/入口名` | R1 |
| 指标描述 | `xxx uv/pv` 换行分隔，点击/曝光分列 | R2 |
| 事件 | 平台链接 + `页面/组件` + 上报要求 + `参数：` 参数表 | R3 |
| 端 | Android、IOS、鸿蒙（按需求裁剪，顿号分隔） | R5 |
| 触发类型 | 点击、曝光（与事件列上报要求一致） | R6 |
| 截图说明 | 生成占位 `【待补截图】`，人工嵌入 | R7 |

## 三、Agent 工作流（五步）

```
输入新需求（自然语言/PRD 片段）
   │
   ▼
①需求解析 —— 识别功能域、入口/模块、涉及资源类型、多端范围
   │
   ▼
②语料检索 —— 在 corpus/ 中按语义相似度找 Top-K 历史方案
   │        （同一功能域优先，如同为"畅听播放器"）
   ▼
③方案生成 —— 严格按 conventions.md 规范 + Top-K 样例 few-shot，
   │        生成 6 列输出行；每个参数必须给出赋值规则
   ▼
④自校验 —— checklist 逐项检查（见下）
   │
   ▼
⑤输出交付 —— Markdown 表格 + 可粘贴 TSV + 未决项列表
```

## 四、自校验 Checklist（生成后必过）

| # | 检查项 | 判定 |
|---|---|---|
| C1 | 指标名含【】功能标记 | 格式 |
| C2 | 指标描述均为 `xx uv/pv` 形态 | 口径 |
| C3 | 事件列含平台链接或【待建事件】占位 | 完整性 |
| C4 | 页面/组件定位符合 `页面/组件` 格式 | 格式 |
| C5 | 每个参数有明确赋值规则（写死/枚举/动态/默认） | 完整性 |
| C6 | 枚举值用中文键:"上报值" 映射表 | 口径 |
| C7 | 触发类型与上报要求一致（都要报 ↔ 点击、曝光） | 一致性 |
| C8 | 端列表与需求覆盖一致，写法 `Android、IOS、鸿蒙` | 格式 |
| C9 | 复用检查：corpus 中已有相同/相似事件则标注"复用" | 防重复 |
| C10 | 无 PII 等敏感字段进入参数 | 安全 |

## 五、参数赋值规则四型（生成时必选其一标注）

| 类型 | 语法示例 | 使用场景 |
|---|---|---|
| 写死型 | `写死 "模式入口"` | 固定 UI 文案/位置标识 |
| 枚举型 | `（歌曲:"2"，MV:"D"）` | 有限资源类型/模式集合 |
| 动态型 | `当前播放内容的id` | 运行时取值 |
| 默认型 | `默认传"default"` | 可空兜底 |

## 六、与 GitHub 开源方案的映射

| 本设计组件 | 借鉴来源 |
|---|---|
| corpus/ 一行一文件结构化语料 | Accoil 的 `.telemetry/*.yaml` 工件模式 |
| YAML 契约（sample-001 中的 yaml 块） | trackboard 的 `trackboard.contract.v1` |
| C9 复用检查（delta 模式） | Accoil 的 `current-state → design → delta` |
| 触发类型与上报要求一致性约束 | 神策"触发时机规范化"理念 |
| few-shot 检索生成 | RAG 通用范式（llama-index 思路） |

## 七、下一步（按优先级）

1. **补语料**：把历史方案逐行录入 corpus/（每行一个 md，含 yaml 块）——语料越多，生成质量越高
2. **人工过一遍 conventions.md**：确认 R1-R7 规范是否与团队实际一致，特别是"IOS"写法、uv/pv 口径
3. **用 1-2 个真实新需求试跑**：验证生成质量，迭代 checklist
4. **后续增强**：截图 ID 引用表（解决 DISPIMG 不可读）、埋点平台链接自动登记

## 八、决策记录（2026-09-21 与产品确认）

| 决策项 | 结论 |
|---|---|
| Agent 形态 | **Skill 提示词方案**（SKILL.md 驱动，在 AI agent 工具中对话式使用，非独立 API 程序） |
| 输入形态 | 产品在**埋点需求文档（Excel）**中填写需求，agent 逐条处理 |
| 输出落盘 | 设计结果直接写回需求文档的**【埋点事件设计】列**（脚本自动备份；已有/新事件都要输出） |
| 交互方式 | **多轮澄清式**：缺失信息先向产品批量提问，不猜测；产品要求直接生成时才标【待定】 |
| 埋点规范 | 团队**飞书文档**为权威源（持续完善），`conventions.md` 为 agent 工作副本，需人工同步 |
| 查重基准 | **全部已有埋点在一个 Excel 表**，由产品导出，放 `data/all_events.xlsx` |
| 端范围 | 不限于三端：Android、IOS、鸿蒙、**Web、小程序、服务端**等，以需求文档标注为准 |
| 语料回流 | 产品确认方案无误并说**"入库"**后，agent 才格式化写入 corpus/（防止错误方案沉淀） |
| 事件链接 | 已有事件引用原链接；新事件 `【待建事件：建议名】` 占位，平台建好后回填 |
